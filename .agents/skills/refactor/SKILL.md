# Refactor

## 目标

在保持现有业务逻辑、接口契约和外部可观察行为不变的前提下，降低代码库的整体复杂度，使代码更少、更简单、更容易理解和修改。

优先删除不必要的代码，而不是增加抽象；优先简化现有结构，而不是引入新的架构。

重构应使代码库更容易维护，而不是仅仅改变代码的组织形式。更少的代码，通常会更好理解和维护。

## 基本原则

- **减少代码**：优先删除无用、冗余和不必要的实现。
- **保持逻辑与行为**：重构不改变现有业务逻辑、外部可观察行为、接口契约和业务规则；可以调整实现方式，但不能借重构修复缺陷或调整功能。
- **避免过度设计**：不为假想需求增加抽象、扩展点或兼容层。
- **职责清晰**：模块和函数应有明确职责，避免重复实现和职责扩散。
- **代码自解释**：优先通过清晰的命名、结构和类型表达意图，不依赖额外的解释性文档或注释。
- **证据驱动**：性能优化必须有实际证据，不为推测性的收益增加复杂度。
- **控制范围**：只处理当前目标相关的问题，不顺手扩大重构范围。

## 重构优先级

按照以下顺序考虑改进，不要求每次重构都执行全部步骤。

### 1. 删除代码

优先删除：

- 无用、冗余或不可达代码；
- 没有实际用途的辅助函数和封装；
- 已确认删除后不会改变现有行为的默认值、fallback、兼容逻辑和条件分支；
- 不再需要的配置、抽象和文档。

删除前应确认代码没有被动态调用、依赖注入、插件发现、配置入口或其他隐式机制使用。不能仅因缺少需求或设计依据就删除现有逻辑；无法确认行为等价时，保留原实现。

不要仅凭代码没有测试或覆盖率低就认定其无用。

### 2. 合并重复代码

- 合并重复的业务逻辑和数据转换。
- 消除不同模块中重复实现的相同规则。
- 统一确实属于同一职责的重复能力。
- 避免通过复制代码形成多个不一致的实现。

不要为了消除表面上的重复而强行统一语义不同的代码。

### 3. 降低嵌套与分支

- 减少不必要的条件嵌套。
- 消除重复判断和冗余状态分支。
- 优先使用清晰、直接的主流程。
- 将复杂逻辑简化为更少、更明确的步骤。

不要为了减少行数而使用难以理解的嵌套表达式，或把复杂判断压缩成难以阅读的一行代码。

### 4. 明确模块职责

- 一个模块承担一个明确的核心职责。
- 缩小职责混乱的模块，明确模块之间的输入、输出和依赖。
- 将真正独立的能力分离，使其可以独立理解、测试和替换。
- 优先通过清晰的接口隔离变化，而不是增加不必要的层次。

不要机械地拆分函数、类或文件。只有职责确实独立、边界清晰时才进行拆分。

### 5. 统一公共能力

- 统一重复的辅助函数、数据转换和公共处理逻辑。
- 保持相同能力具有一致的调用方式和行为。
- 复用已有的公共能力，避免重复造轮子。
- 只有多个调用方确实共享同一职责时，才抽取公共实现。

不要为了未来可能出现的需求提前建立通用框架。

### 6. 改善命名与可读性

- 使用准确、明确的命名表达业务意图。
- 使代码结构能够清楚地表达模块之间的关系。
- 消除不必要的间接调用和跳转。
- 保持主流程直观，减少理解代码所需的上下文。
- 优先让代码本身表达意图，而不是增加解释性注释和重复文档。

注释和文档应保留真正无法从代码直接理解的信息，例如重要约束、非显而易见的设计原因和外部契约。

### 7. 最后考虑抽象与设计模式

只有在职责、变化模式和复用需求已经明确时，才考虑引入抽象或设计模式。

引入抽象前先判断：

- 是否确实存在重复或独立的职责？
- 是否减少了整体复杂度？
- 是否让调用方更容易理解和使用？
- 是否增加了额外的间接层次和维护成本？

如果直接实现更简单、更清晰，就不引入抽象。

### 8. 性能优化必须有证据

- 优先处理已经确认的性能瓶颈。
- 通过 Benchmark、Profiling、监控数据或可重复的测试定位问题。
- 优先减少不必要的计算、数据库查询、网络请求和内存分配。
- 在保证正确性的前提下比较优化前后的结果。

没有充分证据时，不为了微小或推测性的性能收益增加复杂度。

## 代码清理规则

### 未测试的代码

发现代码没有被测试时，先判断它是否必要，而不是默认补充测试。

- 如果承担关键业务行为：考虑补充必要测试，确保后续修改安全。
- 如果存在重复实现：优先合并。
- 如果已确认无用且删除后不会改变现有行为：考虑删除。
- 如果只是某个模块中不必要的独立抽象：考虑内联或内聚到已有实现。
- 如果无法确认其用途：先调查调用关系，不擅自删除。

测试的目的是保护必要行为，而不是为每一段代码寻找存在理由。

### 代码量与复杂度

更少的代码通常更容易理解和修改，但代码行数不是唯一指标。

优先减少：

- 重复逻辑；
- 不必要的分支；
- 无意义的封装层；
- 不必要的状态和数据转换；
- 过度抽象；
- 已确认不会影响现有行为的无用实现。

不要通过缩短命名、压缩格式或把多种职责塞进一个函数来单纯减少行数。

## 执行模式

### Plan：制定重构方案

只分析和提出方案，不修改文件。

1. 明确重构目标和范围。
2. 阅读相关代码及必要的 Design。
3. 追踪调用关系，确认代码用途和依赖。
4. 识别可删除、合并、简化或重新划分职责的部分。
5. 按预期收益、风险和改动范围排列优先级。
6. 明确行为保持要求及验证方式。

输出最有价值的改进项，不生成大量低收益建议。

### Apply：执行重构

根据明确的重构目标或已确认的方案执行修改。

1. 确认当前行为及相关测试基线。
2. 优先执行范围小、风险低、收益明确的改动。
3. 每批修改后运行相关测试，尽早发现行为变化。
4. 清理因重构而失效的代码、测试和文档。
5. 检查 Design、Code、Tests 是否仍然一致。
6. 总结实际修改、验证结果和未解决的问题。

不要为了实现计划而机械执行已经失去必要性的改动。

## 与其他 Skill 的协作

- **Design**：提供当前预期行为、模块职责和设计约束。涉及业务行为或设计契约变更时，先确认设计变更，不以重构为名擅自改变设计。
- **Review**：提供已发现的问题和相关证据。Refactor 可以调查实现细节，但不重复执行完整的代码审查。
- **Test**：验证重构前后的行为是否保持一致，并执行必要的回归测试。

重构过程中如果发现新的问题，可以记录并评估，但不要自动扩大当前任务范围。

如果重构确实需要改变外部行为或业务规则，应停止将其视为纯重构，先明确变更目标并确认相关 Design。

## 完成标准

重构完成时，应确认：

- 必要行为和接口契约保持不变；
- 相关测试已实际执行，结果明确；
- 删除和合并的代码没有破坏隐式依赖；
- 代码复杂度确实降低，而不是转移到其他模块；
- 没有新增功能、修复缺陷或引入不必要的抽象；
- 需要更新的设计文档和测试已同步；
- 尚未验证的风险已明确说明。

达到目标后停止，不为了追求进一步的代码变化而继续重构。
