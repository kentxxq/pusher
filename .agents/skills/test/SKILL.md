# Test

## 目标

通过必要的自动化测试验证代码是否符合 Design，确保关键业务行为正确，并保留可理解、可复查的测试证据。

测试用于证明设计被正确实现，不以测试数量、代码行覆盖率或分支覆盖率作为最终目标。

## 测试使用规则

1. 编写或修改测试前，阅读相关 `docs/design/`，明确需要验证的行为、规则和不变量。
2. 优先检查并复用现有测试，避免重复创建相同目的的测试。
3. 根据被验证的行为和依赖范围选择必要的测试类型，不要求每个功能都同时编写三类测试。
4. 测试应验证可观察的行为和预期结果，而不是简单验证代码能够执行。
5. 执行测试后，记录实际结果，区分通过、失败、跳过和无法执行的情况。
6. 关键测试结果应保留人类可读的日志或报告；涉及用户界面和完整交互流程时，可使用截图或视频作为证据。
7. 不为了让测试通过而随意修改断言、降低验证标准或掩盖真实失败。
8. 不要求为每个函数、每条代码路径或每个假想场景编写测试。

## 测试分类

测试只分为以下三类。

### 1. Unit：单元测试

**目标：快速验证单个模块的逻辑和业务规则。**

- 优先使用真实的待测代码，隔离无关的外部依赖。
- 验证输入、输出、状态变化、业务规则和不变量。
- 执行应当极快，适合频繁运行。
- 不依赖真实数据库、外部 API 或 LLM 服务。

适用于确定性逻辑、数据转换、业务规则和状态处理。

### 2. Integration：集成测试

**目标：验证多个模块及其外部依赖之间的协作是否正确。**

重点包括：

- 数据库读写、事务和数据映射；
- 外部 API 的请求、响应和错误处理；
- LLM 请求、响应解析及结果处理；
- 模块之间的接口契约；
- 配置、序列化、持久化和依赖集成。

根据验证目标使用真实依赖或合适的测试替身。需要验证真实集成行为时，不得仅凭 Mock 测试通过就认定集成正确。

真实外部服务测试应考虑凭据、费用、速率限制和结果不确定性，避免无必要的重复调用。

### 3. E2E：端到端测试

**目标：验证用户操作所触发的完整业务闭环。**

从真实入口开始，经过必要的系统组件，直到获得最终结果。

例如：

```text
用户提交剧本
    ↓
API 接收请求
    ↓
剧本解析
    ↓
生成分镜
    ↓
保存结果
    ↓
用户获取生成结果
```

- 优先覆盖核心用户流程和高风险业务闭环。
- 尽可能验证真实组件之间的协作。
- 涉及 UI 时，可使用浏览器自动化验证页面操作和最终展示。
- 不重复验证大量已经由单元测试充分覆盖的局部逻辑。
- 失败时应尽量保留足以定位问题的日志、请求信息或截图。

E2E 不要求所有流程都使用浏览器。没有 UI 的系统可以从 HTTP API、命令行或其他真实业务入口验证完整流程。

## 测试选择

根据需要验证的行为选择最合适、成本最低的测试类型。

| 验证目标 | 优先选择 |
|---|---|
| 单个模块的业务规则 | Unit |
| 数据库、外部 API、LLM 或模块间协作 | Integration |
| 用户操作的完整业务闭环 | E2E |

优先使用 Unit 覆盖确定性逻辑；只有涉及依赖协作时才增加 Integration；只有需要验证完整流程时才增加 E2E。

不要仅因为某个功能重要，就机械地为它增加所有类型的测试。

## 测试有效性

检查测试是否真正证明了预期行为：

- 断言是否验证了有意义的结果，而不只是执行成功。
- 是否验证了重要的业务规则和不变量。
- 测试是否与当前 Design 一致。
- 是否存在过于宽泛、永远通过或无法发现真实错误的断言。
- 是否通过 Mock 隐藏了本应验证的集成行为。
- 测试失败是否能够提供足够的信息定位问题。

测试通过不等于实现一定正确。必要时应结合 Design 和实际代码独立判断。

## 测试缺口与代码处理

发现未被测试覆盖的代码时，不要默认补测试。

先判断：

1. 这段代码是否承担关键业务行为或重要职责？
2. 是否有明确的 Design、接口契约或真实需求支持它？
3. 是否确实需要通过测试保证其行为？
4. 是否属于冗余实现，可以删除、合并或内聚到已有模块？

处理原则：

- **关键行为缺少验证**：补充能够证明该行为的最小必要测试。
- **必要代码缺少测试，但风险较低**：根据实际风险决定是否补充，不机械追求覆盖率。
- **代码没有明确职责或需求依据**：评估删除、合并或简化，而不是为了保留它强行编写测试。
- **无法确认代码是否必要**：说明依据不足，不擅自删除。

不得仅凭代码未覆盖就认定代码无用，也不得仅为了提高覆盖率而保留不必要的实现。

## 执行与验证

测试工作遵循以下流程：

1. 根据 Design 明确需要验证的行为。
2. 检查已有测试，选择必要的测试类型。
3. 编写或调整测试。
4. 实际执行相关测试，并检查真实结果。
5. 失败时分析原因，区分实现缺陷、测试缺陷、环境问题和外部依赖故障。
6. 保存必要的验证证据。
7. 总结验证结果及尚未验证的范围。

不要将未执行的测试描述为已通过，也不要将环境导致的无法执行描述为代码缺陷。

## 测试证据

测试结果应尽量保留人类可读的证据：

- **日志**：保留关键输入、执行阶段、错误原因和必要上下文，避免输出无法理解的大量原始信息。
- **测试报告**：记录测试名称、通过与失败情况，以及必要的失败详情。
- **截图**：用于证明页面状态、视觉展示或关键交互结果。
- **视频**：用于展示多步骤交互、完整用户流程或难以通过单张截图表达的问题。

根据测试类型和实际需要选择证据，不要求每次测试都生成截图或视频。

证据应足以让人复查测试是否真正执行，以及结果是否符合预期。

## 完成标准

测试任务完成时，应明确说明：

- 执行了哪些测试类型；
- 实际运行了哪些测试；
- 通过、失败、跳过或无法执行的情况；
- 是否发现 Design 与实际行为不一致；
- 是否存在尚未验证的关键行为；
- 测试日志、报告或其他证据保存在哪里。

以关键行为得到充分验证为目标，不以覆盖率达到某个数字作为完成条件。
