# Code Review

## 目标

通过阅读 Design、Code 和相关 Tests，发现正确性、设计质量、性能及代码品味问题。

优先识别真实缺陷和不必要的复杂度，不为追求完美而提出低价值建议。

## 1. 正确性与设计一致性（Correctness）

阅读相关 `docs/design/`，结合实际代码及调用关系，检查：

- **设计符合性**：实现是否满足设计目标、业务规则、模块职责和系统边界。
- **行为一致性**：不同入口、调用路径及相关模块是否存在前后矛盾的行为。
- **逻辑正确性**：数据转换、状态变化、错误传播和接口契约是否正确。
- **实现完整性**：是否遗漏设计要求的关键流程或行为。
- **不变量**：是否违反设计约定的数据关系、状态约束和不变量。
- **设计漂移**：是否存在设计与代码不一致、过期设计或未经定义的新行为。

发现偏差时，不直接假定 Design 或 Code 哪一方正确，明确指出冲突及证据。

## 2. 设计与性能问题（Architecture & Performance）

检查明显不合理的结构和性能开销：

- 模块职责混乱、循环依赖、不合理的跨层调用。
- 重复实现已有能力，或引入没有实际必要的抽象和设计模式。
- N+1 查询、重复数据库访问、重复外部 API 请求。
- 阻塞异步流程、无界并发、不合理的资源生命周期。
- 明显低效的算法、重复计算、不必要的数据复制和序列化。
- 资源泄漏或缺少必要的释放机制。

区分可以通过代码确认的缺陷与需要 Benchmark、Profiling 才能确认的性能瓶颈。

不因推测性的性能收益提出复杂优化方案。

## 3. 代码质量与品味（Code Quality）

优先检查复杂度是否必要，而不是单纯追求代码形式上的优雅。

- 是否存在重复、冗余、无用或不可达代码。
- 是否存在没有 Design、Test 或外部契约依据的条件分支。
- 是否存在静默 fallback、无依据的默认值或自动纠错。
- 是否捕获异常后无明确理由继续执行，掩盖真实错误。
- 是否通过默认值隐藏非法状态或违反不变量的数据。
- 是否在多个内部 Service 中重复校验同一个不变量。
- 是否为假想的边界情况增加过多 defensive code。
- 是否存在不必要的嵌套、辅助函数、封装层或过度抽象。
- 是否可以复用已有能力，提高一致性和可读性。
- 是否为一个极小概率或假设中的场景，在主路径上插入分支、参数或特殊返回，使正常流程变得难以阅读或难以推理；这类情况应优先在边界隔离处理。

外部不可信输入应在边界校验，内部模块默认遵守已经建立的契约。

仅当 Design、测试、外部契约或已知真实问题有依据时，才认为特殊边界情况需要额外处理。

## 审查方式

1. 确定审查范围，优先阅读相关 Design、代码和测试。
2. 追踪必要的调用链与数据流，不只检查单个文件。
3. 对照设计，检查正确性、行为一致性和不变量。
4. 检查明显的架构、性能和代码质量问题。
5. 对发现的问题核实证据，避免主观推测和误报。
6. 输出问题清单，不直接修改代码、测试或设计。

默认审查全部维度；调用方可以指定只检查某个维度。

## 输出要求

仅报告有明确依据、值得处理的问题。

每项问题包含：

- **位置**：文件及相关代码位置。
- **问题**：具体缺陷或不合理之处。
- **证据**：对应设计、代码、调用关系或测试结果。
- **影响**：正确性风险、性能损失或维护成本。
- **优先级**：P0 / P1 / P2。
- **建议方向**：简要说明如何处理，不展开详细重构方案。

优先级：

- **P0**：严重正确性、安全性或数据完整性问题。
- **P1**：明确的行为偏差、重要性能问题或明显设计缺陷。
- **P2**：有实际改进价值的代码质量和可维护性问题。

没有发现值得处理的问题时，直接说明，并标记未检查或无法验证的范围。

## 约束

- Review 默认只读，不修改任何文件。
- 不重复承担 Test 的动态验证职责。
- 不重复承担 Refactor 的详细方案设计和代码修改职责。
- 不将测试覆盖率低直接等同于代码质量差。
- 不将代码量多直接等同于设计不合理。
- 不要求为假想 Edge Case 添加代码。
- 不因个人风格偏好或微小收益提出修改。
- 没有充分证据时标记为待验证，不报告为确定缺陷。
- 审查结束后停止，不自动进入重构。
