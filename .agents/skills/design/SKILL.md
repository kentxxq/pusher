# 设计文档

## 设计文档使用规则

对于实质性修改：

1. 实现前先阅读相关的 `docs/design/` 文档，并结合实际代码验证设计是否仍然有效。
2. 将设计文档视为当前预期设计，但不盲目相信文档；发现设计与代码不一致时，应明确识别偏差，不擅自假定哪一方正确。
3. 如果修改影响行为、架构、接口契约、数据模型、模块职责、数据流或关键设计决策，必须在同一次修改中同步更新相关设计文档。
4. 设计文档只描述当前有效设计，不记录聊天记录，也不维护按时间排列的开发日志。
5. 完成修改前，检查设计文档、实际实现和测试是否保持一致。

### 抽象层级

设计文档应比代码高一个抽象层级，只记录理解和维护系统所必需、未来修改时仍需要主动了解的事实。

不要记录：

- 可以直接从代码中读取的实现细节；
- 函数级调用顺序；
- 局部算法步骤或伪代码；
- 临时实现状态；
- 无长期价值的细节。

如果代码发生变化，但系统行为、架构、边界、规则、模块职责、数据流或关键设计决策没有变化，则不需要修改设计文档。

### 整体架构与子系统设计

项目整体架构属于 Design，统一放在 `docs/design/architecture.md`，不由 `AGENTS.md` 取代。

- `architecture.md` 描述整体架构，包括主要子系统、职责边界、依赖关系、核心数据流和关键交互，优先使用简洁的 Mermaid 图表达。
- 子系统设计文档描述自身的目标、边界、规则、模块职责、流程和关键决策。
- 整体架构只保留理解系统所必需的信息，不重复子系统内部的详细规则。
- 同一个事实只维护一个权威位置，其他文档通过引用或简要说明关联关系，避免重复描述。
- 修改影响子系统职责、边界、依赖关系或跨模块数据流时，检查是否需要同步更新 `architecture.md`。
- 仅改变内部实现方式、未改变整体架构事实时，不需要更新 `architecture.md`。
- 如果不存在相关设计文档，只有在该子系统足够重要、后续确实需要长期保留设计上下文时，才向用户提议创建。未经用户允许，不得自动添加设计文件。

## 设计文档结构

根据实际需要选择以下章节：

1. **目标**：说明这个模块要解决什么问题，以及必要的职责范围。
2. **边界**：明确负责什么、不负责什么，避免职责扩散。
3. **规则**：记录必须遵守的业务规则、技术约束、数据关系、不变量和限制。
4. **模块职责**：说明核心模块分别负责什么，避免职责重叠。
5. **流程**：描述关键业务流程、数据流向或状态变化，优先使用 Mermaid 表达。涉及多个模块时，明确重要数据的输入、输出和持久化位置，不展开函数级调用。
6. **关键决策**：记录重要设计取舍、选择原因，以及仍有参考价值的替代方案。

不要求为了补全结构而添加没有实际价值的内容；没有必要时可省略对应章节。

## Design 与 Notes

`docs/design/` 记录：

> 系统当前是什么、如何工作。

`docs/notes/` 记录：

> 为什么曾经这样设计，以及仍有价值的历史背景。

Note 属于历史上下文，可以定期合并、精简或删除已经失去参考价值的内容。

默认先阅读 Design。只有在以下情况需要查询相关 Note：

- 当前设计或代码的意图不明确；
- 需要理解某个重要取舍为什么存在；
- 准备改变已有关键设计决策；
- 需要了解曾经考虑或放弃过的替代方案。

不主动记录 Note。不要把普通实现过程、临时讨论或可以从当前 Design / Code 直接看出的内容写入 Note。

设计发生变化后，Design 更新为当前有效状态；只有仍有长期参考价值的历史原因才保留在 Note 中。
